# 系统与链路评估（2026-10-13）

当前链路适合个人低流量使用：Grok 负责直接查证来源和条件，MCP 负责授权、保存、时效、规格与利润核验，网页只读展示。继续使用现有 Node/Vercel/private Blob，没有新增数据库、队列或采集平台。

## 本轮修复

| 问题 | 改进 | 验证 |
| --- | --- | --- |
| 购买条件未确认或已过期，API 仍能返回数字净利润，Bot 可能误用 | 所有 pending_confirmation 的 netProfit 统一为 null；证据价格保留 | 纯预览、本地 HTTP 和独立云 handler 回归；有效151/120/61等利润仍保留 |
| 同一 SKU 有冲突容量、地区、成色，解析器只取第一项；两边复制同一错误描述可能通过 | 冲突字段按缺失处理，保持待确认；重复相同字段仍兼容 | 完整购买+回收的 preview 回归、RAM/容量与旧匹配器回归 |
| 持续失败/限流仍固定30秒请求，增加故障期负载 | 有界指数退避，遵循 Retry-After，前后台切换/手动刷新不绕过退避；成功复位 | 虚拟时钟覆盖连续失败、成功恢复、429和前后台切换 |
| 看板正常读取无业务变化却仍写回完整私有状态 | 仅在只读工具的业务状态完全不变时跳过业务写回；清理仍 CAS 持久化 | 独立进程模拟：普通读取2次写入、带清理3次；未知写不重试、有限CAS重试继续覆盖 |

权限、每项幂等、一次通知尝试、identity强ETag、私有Blob、七工具协议和只读网页保持。改动不需要新配置或换Token，不迁移、重置或批量改写生产记录。

## 仍然成立的边界

- 来源真实可靠仍依赖 Bot 直接核实和证据质量。来源白名单及 verified 字段不等于平台对价格作保证；不新增自动抓取、支付或下单工具。
- 用户目前不使用 Telegram，网页查询是已启用的用户端结果入口；不能宣称主动提醒已经送达。
- 单个 Blob 加 CAS 适合低频私人使用。普通查询仍有分布式限速的写入成本；不为省操作数撤掉全局限速或并发保护。纯 preview 仍零 Blob 操作。
- 近期记录上限200、单机会报价20、旧线索版本10；幂等收据和通知保护不会为腾位置而提前删除。高频反复核验同一活动可能达到容量上限并明确拒绝；扩大使用量前应单独设计保留/归档策略，不能静默丢掉审计。
- 作废沿用近期7天保留条件，通知摘要30天；作废不能撤回已经开始发送的通知。没有永久审计、常驻任务或定时采集承诺。

本轮本地模拟不证明 Grok 已核实任何真实商品。生产验证只使用现有授权下的只读查询和纯预览，不新增生产模拟记录。
